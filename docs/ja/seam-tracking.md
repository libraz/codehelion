# seam の追跡

seam とは、同じ意味論が複数の場所に実装されていて、かつ実際に連動して変更されてきたパスの集合です。同じ規則を持つ 2 つのフロントエンド、整合していなければならない描画器とエクスポータ — 写しはコードの側にありますが、それらが一組であるという証拠は履歴の側にあります。

codehelion は seam を自分で探しにいきません。seam は人が `codehelion.toml` に書き下すものであり、このページのすべての検査はその台帳を読みます。理由は、実行のたびに履歴から対象を計算し直すゲートは、誰もコードを変えていないのに今日は通って明日は落ちるからです。台帳をコミットしておけば、レポートが何について述べているかを読み手が引けます。

ここに書くことはすべてローカルの `.git` だけから計算します。外部に送るものはなく、実行経路に言語モデルは登場しません。

## 台帳を書く

```toml
[[seam]]
id = "frontend-c-cpp"
members = ["crates/codehelion-frontend-c/**", "crates/codehelion-frontend-cpp/**"]
note = "same semantics implemented twice across the two frontends"
```

`members` はリポジトリ相対のパスに対する glob で、seam には 2 つ以上必要です。`id` はレポート中で seam を名指しする識別子です。`note` は何も読まない自由記述で、次に読む人のために置いてあります。

設定は別の `[seam-tracking]` 節に置きます。TOML では同じ名前を array of tables と table の両方には綴れないためです。[設定](configuration.md#seam)を参照してください。

## 3 つのコマンド

```sh
codehelion history                    # コミット範囲に何があるか
codehelion seam                       # 台帳の seam を計測する
codehelion seam --suggest             # 共変更だけから候補を挙げる
codehelion guard                      # 作業ツリーを台帳に照らす
codehelion guard --since v0.4.0       # 代わりに revision 範囲を見る
codehelion guard --paths crates/codehelion-frontend-c/src/lex.rs
codehelion guard --deny-asymmetric    # 非対称変更があれば exit 3
```

`history` はコミットの記録だけを読みます。範囲に何件のコミットがあるか、それらが fix / feature / その他のどれに分類されるか、範囲の最初と最後がどのコミットかを出します。ソースファイルを開かず台帳も要らないので、そのどちらも無いリポジトリで最初に走らせるコマンドになります。

`seam` は台帳の項目ごとに、非対称変更が何件あったか、そのうち何件が breach になったか、直近の breach がいつだったかを報告します。`--until <rev>` で範囲の終端を固定でき、これが世代の異なる数値を並べられる条件になります。

`guard` は 1 つの変更を台帳に照らします。既定では作業ツリーと `HEAD` の差分を読み、`--since <rev>` を付けるとその revision から `HEAD` までの差分を読みます。`--paths <p>...` が問うのは別のことで、編集した後ではなく編集する前に訊く形です。指定したパスがどの seam に属し、一緒に動かす必要のあるメンバーがどれかを述べます。このモードは台帳だけを読み、git を開きません。

台帳が無い、または空の場合はエラーになりません。`guard` は何も報告せず `0` で終わります。

## 数値が意味すること

**非対称変更**とは、seam のメンバーの一部だけを触り、残りをそのままにしたコミットのことです。

**breach** とは、非対称変更の後 `breach-window` コミット以内に、その非対称変更が触らなかったメンバーを触る `fix:` コミットが来た事象のことです。窓を日数ではなくコミット数で数えるので、作業がどれだけの速さで進んだかで値が動きません。

非対称変更は形であって判定ではありません。正しい非対称変更はいくらでもありますし、メンバーの片方だけに理由がある変更も起こります。breach はより強い言明です。そのリポジトリはその非対称の代償を一度すでに払っており、seam が実在しかつ有害であることの証拠になります。

どちらの数値もコードを測ってはいません。述べているのはパスの集合に起きたことであって、そのパスの中身が重複しているかどうかではありません。それに答えるのは[スキャン](analysis-modes.md)です。メンバーが実は独立していた台帳の項目は、非対称変更をいつまでも出し続けて breach を 1 件も出しません。その形が、台帳から外す合図です。

`guard` は既定では報告するだけで `0` を返します。`--deny-asymmetric` を付けたときだけ、非対称変更があれば `scan --fail-on-findings` と同じ `3` で終わります。実行単位の抜け道は意図的に設けていません。既定が報告である以上、誰かが意図的に失敗を要求したときにしか失敗は起きず、そこに例外フラグを足せば、その人が立てたフラグを無効化するためだけのものになります。報告が多すぎる seam は、`members` をより細かく切り直します。

## 候補提示と、昇格を人が行う理由

`codehelion seam --suggest` は共変更だけから seam の候補を挙げ、その根拠となる数値を併記します。

```
support(a, b)     = 両方を触ったコミット数
confidence(a→b)   = support(a, b) / a を触ったコミット数
coupling(a, b)    = min(confidence(a→b), confidence(b→a))
```

`coupling` が片方向の confidence ではなく最小値を取るのは、何を変えるときにも巻き込まれるパス — トップレベルのマニフェストやロックファイル — が、ツリー全体と結合しているように読めてしまうのを避けるためです。`min-coupling` と `min-support` を下回る候補は出しません。共変更を数える単位は、ファイル名そのものではなく、各パスの先頭 `suggest-depth` 成分です。

`max-commit-size` より多くのパスを触るコミットは coupling の計算から外します。大規模なリネームや整形の一括適用は、たまたま含まれた全ペアに support を配ってしまうためです。ただし breach の判定からは外しません。大きなコミットが seam を破ったのなら、それは破ったことに変わりないからです。

すでにツリーに無いディレクトリを含むペアは提示しません。1 つに統合された 2 つの crate は、どちらかが現れたすべてのコミットで一緒に動いているので、永久に完全な coupling として読めてしまいます。誰も手を打てない提示です。ディレクトリがまだあるかを確かめることが、`--suggest` が履歴の外に読みにいく唯一のもので、ファイルは開きません。

`--suggest` が台帳へ書き込むことはありません。候補を昇格させるのは「このコードが何を意味するはずか」という言明であり、それを人の手に残すことが、履歴が伸び続けてもゲートの対象を動かさない条件になります。

## 2 回の実行を比較可能にするもの

- コミットは `(committer time, commit id)` の昇順で走査します。git の既定の走査順を引き継がず、ここで固定します。同時刻のコミットは commit id で順序が決まります。
- rename 検出は使いません。リネームは delete と add として読みます。rename 検出は類似度ヒューリスティックであり、閾値とともに動く結果は 2 回の実行を比較する土台になりません。
- fix かどうかは Conventional Commits の prefix だけで決めます。メッセージ本文に対する自然言語の検索は行いません。
- マージコミットは第一親だけを辿ります。
- どの出力にも、算出に使った設定のダイジェストと、読んだ範囲の最初と最後のコミットが入ります。これが無いと、動いたのが数値なのか設定なのかを区別できません。

## 履歴に対する要求

リポジトリが履歴を持っている必要があります。shallow clone は読めません。CI では `actions/checkout` に `fetch-depth: 0` を指定することを意味します。既定の depth 1 では 1 コミットしか見えません。

breach には Conventional Commits が必要です。`fix:` prefix を持たないメッセージのリポジトリでは breach が 1 件も出ません。非対称変更はメッセージではなくパスについての判定なので、どちらでも検出できます。

`history-limit` は新しい順に何件のコミットを読むかの上限です。これは天井であって床ではありません。若いリポジトリの数値が薄いのは背後にある履歴が少ないからで、数件のコミットしか下に無い seam は、数値が示唆するほどのことを述べていません。

## これで見えないもの

同一ファイル内の重複には時間軸が付かず、片側のメンバーだけを直した正しい変更も非対称変更として報告され、ファイルの履歴は移動した場所で切れます。[制限](limitations.md)を参照してください。
