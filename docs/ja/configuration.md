# 設定

`codehelion scan` はスキャンルートの `codehelion.toml`（任意）を読み込みます。`codehelion config init` は全項目にコメントの付いたテンプレートを、各キーの組み込み既定値のまま書き出します。`codehelion config show` はファイルと既定値を解決したあとの有効な設定を表示します。

```sh
codehelion config init      # codehelion.toml を生成
codehelion config show      # この実行が使う設定と、その出所
```

## ファイルをどこから読むか

`codehelion.toml` は scan root 自身からしか読まず、親ディレクトリから継承することはありません。scan はどの設定に従ったかとその出所を報告するものであり、読んでいる木より上にある誰も指定していないファイルはそれに当たらないからです。`--config <file>` を使えば、どこにあるファイルでも明示的に指定できます。

2 つの設定は意図的に設定キーではなくフラグにしてあります。設定ファイルはスキャン対象のツリーの**中から**見つかるものだからです。1 つは `--untrusted` で、その対象が自分で決めないことこそが要点です。もう 1 つは `--allow-execution` で、設定キーにすると、許可の対象であるコード自身が許可を出すことになります。

## 何をスキャンするか

```toml
# include = []                      # 含めるパス glob。空ならすべての対応ソース
# exclude = []                      # include から除くパス glob
# min-clone-tokens = 20             # 報告する最小クローン長（トークン数）
# entropy-ratio-floor = 0.60        # これを下回る正規化エントロピーは退化した繰り返し
# literal-normalization = "full"    # "preserve" / "category" / "full"
# database = ".codehelion/audit.db" # ローカルデータベースの場所
# jobs = 4                          # frontend の read/lex worker 数。省略で自動
```

`jobs` が決めるのは frontend の read/lex worker スレッド数だけで、clone grouping と report rendering は serial です。省略した場合の worker 数はホストの並列度から自動で決まります。テンプレートに書かれている値は例であって既定値ではありません。

## 言語と、ひとつだけ曖昧な拡張子

```toml
[languages]
# rust = true
# c = true
# cpp = true
# headers = "detect"                # 拡張子 ".h" を読む文法。"detect" / "c" / "cpp"
```

`.h` は C と C++ が共有する唯一の拡張子で、どちらの文法で読むかがその中身の見え方を決めます。C++ ヘッダを C として読むと、エラー回復によって何も宣言しない形へ崩れ、本来の重複を隠す一方でクラス本体どうしの重複を捏造します。

`detect` は拡張子が曖昧でないファイルを数えて多数派に従います。数えるものが無い木、つまりヘッダのみのライブラリでは、ヘッダ自身を読んで C++ にしか書けない綴りを探し、1 つでも見つかればその実行全体が C++ になります。この選択は実行の build variant に含まれるため、異なる文法で読んだ結果どうしが比較されることはありません。

## priority

```toml
[priority]                          # 整数シェアとして読む
# maintenance-risk = 2
# refactoring-ease = 1
```

設定できるのは合成のみです。重複を残す費用と取り除く費用はコード側の性質についての問いであり、それを変えてしまう設定があると 2 つのプロジェクトのレポートが比較できなくなります。設定値がどうであれ、すべての finding は 3 つの指標を持ちます。両方を 0 にすると clone confidence だけでレポートが並びます。

## 抑制

ポリシーの全体は[抑制](suppression.md)にあります。キーは次のとおりです。

```toml
[suppression]
# paths = []
# vendored-paths = [...]            # 既定で隠す。[] にすれば他と同じように読む
# symbols = []                      # 所属ユニット名に対する glob
# clone-ids = []                    # 安定クローングループ ID（hex、前方一致は 8 文字以上）
# generated-markers = ["@generated", "do not edit", "automatically generated", "auto-generated", "autogenerated"]
# test-paths = [...]
# test-code = "rank-down"
# split-pairs = "rank-down"
# width-family = "hide"

[suppression.boilerplate]
# trivial-body = "rank-down"
# forwarding = "hide"
# macro-repetition = "rank-down"
# guarded-dispatch = "hide"
# configured-answer = "hide"
# composed-answer = "hide"
# built-answer = "hide"
```

リスト型のキーは設定すると既定値に追加するのではなく置き換えます。`generated-markers` が組み込みのバナーを並べて書いているのはそのためです。

## semantic ルール

```toml
[semantic]
# disabled = ["sequence-pipeline-v1"]
```

restricted Semantic のルールは既定ですべて有効です。安定したルール ID をここに挙げると、検出器全体を緩めずに、このプロジェクトでだけ無効化できます。

## helper の場所

```toml
[helpers]
# rust = "/opt/codehelion/codehelion-backend-rust"
# clang = "/opt/codehelion/codehelion-backend-clang"
```

hermetic な CI や `PATH` の外への導入で使います。これらは `--config` で名前を指定した設定ファイルからのみ読みます。このファイルはスキャン対象のツリーの中から見つかるものであり、リポジトリが「自分をスキャンするプログラム」を選べてはならないからです。scan root で見つかったファイルの中では、この節は無視され、その旨の注記が出ます。helper を固定するには `--helper rust=<path>` を渡すか、`--config` でファイルを指定してください。

## リソース上限

発火した上限はすべてレポートに計上されます。

```toml
[limits]
# max-file-bytes = 2097152          # これより大きいファイルは飛ばして計上
# parse-timeout-ms = 10000          # 決定的な parse 作業量上限（wall-clock time ではない）
# helper-timeout-ms = 300000        # Semantic helper 応答の期限
# posting-cap = 64                  # ペア生成に入る posting list の最大長
# pair-budget = 1000000             # ペア生成 pass ごとの候補ペア数
# near-miss-delta = 0.05            # Type-3 の閾値直下の診断帯
# near-miss-cap = 1000              # report ごとに保持する near miss 数
# sibling-candidate-budget = 50000
# sibling-per-group-cap = 8
# sibling-total-cap = 1000
# signature-sibling-candidate-budget = 50000
# signature-sibling-per-group-cap = 8
# signature-sibling-total-cap = 1000
# signature-sibling-max-units-per-signature = 8
# verification-budget = 1000000     # 精密検証に送るペア数
# max-alignment-cells = 4000000     # アラインメント 1 回あたりの動的計画法セル数
# max-component = 1024              # 1 つの塊として比較する関連ユニットの最大集合
```

`parse-timeout-ms` は wall-clock の期限ではなく、互換ミリ秒（入力 256 バイトを 1 ミリ秒とみなす）で測る決定的な作業量の上限です。同じツリーなら速いマシンでも遅いマシンでも同じ場所で上限に達します。

`posting-cap` と `pair-budget` は両モードをまとめて上書きします。省略した場合、各モードは自分の計測が選んだ既定値を保ちます。モードによってペアにするものが違い、同じツリーでも候補数が桁で異なるためです。待てないほど時間のかかるスキャンを区切りたいときに設定してください。その場合、レポートは上限が何件を未検査のまま残したかを述べます。

`signature-sibling-max-units-per-signature` はリソース上限ではなく珍しさの閾値です。ツリーの大部分が共有するシグネチャは、重複ではなく作業を提案するだけなので、証拠であることをやめます。[制限](limitations.md)を参照してください。

## 直前の実行について述べること

```toml
[report]
# churn-top = 100
```

各実行の上位いくつのグループを比較して「見る価値のあった作業がどうなったか」を述べるかを決めます。合計は進捗ではなく重複量を数えるものであり、数千件のうち数件を片付けても合計はほとんど動きません。そのため比較は各実行の上位に対して行います。

## ローカルデータベース

各スキャンは既定で `.codehelion/audit.db` に永続的なローカル監査データベースを作ります。置き場所は scan root を含む Git リポジトリの直下で、サブディレクトリをスキャンしたときに新しいデータベースを作らずリポジトリのものを使い続けるためです。どのリポジトリにも属さない scan root は自分の下に持ちます。場所は `--db <path>` で上書きできます。

リポジトリの `.gitignore` に `.codehelion/` を追加してください。このデータベースは捨ててよい build cache ではありません。レポートと churn の要約が導出される実行履歴が、ここにあります。

完了したスキャンはここに保存され、text / JSON / SARIF レポートはそのスナップショットからのエクスポートです。ツリーと設定が変わらなければ既存の完了 run を再利用し、`--no-reuse` なら新しい run を記録します。再利用が省くのは実行の記録側の半分で、`-v` は 2 つの半分を別々に表示するため、その費用は推測ではなく実測できます。

```sh
codehelion cache status        # 場所・サイズ・中身
codehelion cache prune --force # 保持上限を適用して圧縮
codehelion cache clear --force # ローカル監査データベースを恒久的に削除
```

`prune` は既定で単体の artifact 解析を新しい順に 20 件、各種 comparison をそれぞれ新しい順に 20 件残します（`--keep-artifacts` と `--keep-comparisons` で変更できます）。`prune` も `clear` も保持済みの履歴を削除するため、どちらも明示的な確認フラグが必要です。

別のスキーマで書かれたデータベースが移行されることはありません。既定のパスでは、そのデータベースをそのまま残し、隣の `audit-v<スキーマ>.db` へ記録して、どちらのファイルを使ったかを報告します。`--db` で名前を指定したデータベースの場合は、指定されたパスを無視して別の場所へ書くことになるため、代わりにエラーとします。`codehelion doctor` はディレクトリ内の監査データベースをすべて挙げ、このビルドで開けるものと、実行が選ぶものを示します。
